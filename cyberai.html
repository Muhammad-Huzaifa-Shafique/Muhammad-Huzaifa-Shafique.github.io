CyberAI: Threat Triage ML Pipeline

An applied machine-learning project from a graduate AI course: a scikit-learn scoring pipeline with drift monitoring and a human-review queue, a retrieval assistant that cites its evidence, and a rule-based baseline you can run on this page. Cyber-threat triage is the test domain.

Relevant to: machine-learning pipelines, scikit-learn, logistic regression, anomaly detection (Isolation Forest), elastic-net regression, drift monitoring, human-in-the-loop review, retrieval-augmented generation (RAG), TF-IDF retrieval, sentence embeddings, LLM integration (Ollama, OpenAI), prompt design, regression testing, Python, JavaScript, SQLite.

What it does

Three parts work together. A rule-based baseline scores links, emails and PDFs and returns Clean, Suspicious or Malware with the reasons. It adds points for VirusTotal results, blocklist hits, SPF, DMARC and DKIM results, look-alike domains and phishing wording, and it shows DNS records and registration data beside the verdict without scoring them. An ML pipeline scores indicators in a local cache. A retrieval assistant answers questions from that cache and shows its evidence.

The rules matter to the ML side because they are the baseline a trained classifier would have to beat. The evaluation that would show whether it does has not been run yet (see Limits).

Live threat feeds were hard to scrape reliably, so I seeded the cache with public cybersecurity datasets from Hugging Face as stand-ins. Together with real triage results, they make up the cache.

What runs here
Link parsing, the warning-sign rules for domain names, the look-alike and extra-subdomain check against the trusted list, the Unicode-letter check, the email wording and Reply-To rules, and the verdict thresholds. It is the logic of CyberAI.py, ported to JavaScript.
What does not run here
VirusTotal, DNS records, registration data (RDAP), DNS blocklists, SPF, DMARC and DKIM. They need the internet or a key. A Clean verdict here means only that the offline rules found nothing. It does not mean the link or the email is safe.

I tested this port against the Python code on 28,600 cases. How I tested it, and what the testing showed about the rules.

The ML pipeline

  1. Ingest. Connectors write indicators (URLs, domains, text) into a local SQLite cache.
  2. Features. Numeric features from each record, plus a bag of words over its text limited to the 300 most frequent words.
  3. Score. Logistic regression returns the probability that an indicator is malicious.
  4. Outliers. An Isolation Forest (contamination 0.05, so about 5% of training points count as outliers) returns an anomaly score.
  5. Risk. An elastic-net regression predicts a 0 to 1 risk score. Its target is each record's severity field divided by 10.
  6. Drift. For each numeric feature, the monitor measures how far the new batch's mean moved from the baseline mean, in baseline standard deviations. It averages these and alerts above 0.25.
  7. Review. Any score within 0.15 of 0.5 goes to a SQLite review queue, so a person decides the cases the model is least sure about.

The retrieval assistant

The chat assistant is offline-first. If a message contains a URL, a file or an email, it runs the triage tool. Otherwise it searches the local cache with TF-IDF. Code that loads a MiniLM embedding index is in the file, but this version of the chat does not call it. It shows the answer, why it answered that way, and the evidence passages, and it appends each exchange to a chat log that the search ignores. Separately, it saves question-and-answer pairs back into the cache (the 25 pairs above: 18 triage write-ups and 7 whose saved answer is the word None), and later questions can find them. The code calls this self-training. Nothing is trained: the assistant's earlier answers become searchable evidence, so a wrong answer can come back as evidence too.

When an LLM is configured (Ollama with llama3 by default, or an OpenAI model) it writes the answer text, at temperature 0.3, from the evidence passages. These are the two prompts, as the code builds them.

You are a cybersecurity assistant. Write a clear, factual, structured answer.
Cite evidence inline with bracketed numbers [1], [2], ... referring to the sources below.
Do NOT invent facts not supported by the sources. If sources are weak or off-topic, say so briefly.
Give a thorough, multi-paragraph explanation with bullets where helpful.

Both prompts give the model the facts it should use (the evidence list, the triage result) and say what shape the answer takes. The first one also tells the model what to do when the evidence is weak.

Testing the browser port

The live box is a port, so it has to be tested against the original. A script imports the real CyberAI.py with its internet calls replaced by stubs, gives the same input to both versions and compares the verdict, the score and every reason. It also compares the three library behaviours the rules rely on: URL parsing (urllib.parse), string similarity (difflib) and splitting a domain from its public suffix (tldextract).

The cases mix hand-written edge cases with seeded random ones: odd schemes, user info, bracketed IPv6 hosts, Unicode and punycode names, capital letters, Reply-To variants, very long strings, and emails built to reach 5 points, because the Malware threshold is rarely hit otherwise. To check that the test can fail, I broke the port in 15 places on purpose (thresholds, caps, operators, message text), one at a time. The test caught all 15.

What testing showed about the Python rules

Porting the rules and testing them turned up four behaviours worth knowing. I have not changed the Python tool, and the port copies these behaviours so that the two versions agree.

  • The look-alike check is case-sensitive for email addresses. support@paypa1.com is flagged as a look-alike of paypal.com. support@PAYPA1.COM is not, and gets no look-alike point.
  • The Unicode-letter check does not see punycode. pаypal.com with a Cyrillic "а" (U+0430) scores 2, but its ASCII spelling xn--pypal-4ve.com scores 0.
  • The keyword rule matches pieces of a domain name, so an ordinary name such as freecodecamp.org (it contains "free") counts as a warning sign.
  • In the full tool, each SPF and DMARC result adds one point, including "SPF found" and "DMARC found". An email with a sender domain therefore scores at least 2 there and can never be Clean. I read this in the code and in the project's own README, and I did not run live lookups for it.

These are small, and a labeled evaluation set is the kind of thing that would surface them. They are one more reason I report no accuracy for the rules.

Limit. I could not install the tldextract package where I ran the tests, so the reference run used a stand-in I wrote from its documented algorithm and the same Public Suffix List snapshot (28 December 2025). The domain-splitting comparison therefore shows that the port agrees with that stand-in. I checked the stand-in against 13 known examples. The test scripts use the real package when it is installed, but I could not run that path. The PDF and DNS libraries were also replaced by stubs, so PDF files are not read and the box takes pasted text. The reference run used Python 3.13.

Limits

  • I have not measured accuracy. The code has a hold-out evaluation command (a random 80/20 split), but the saved project has no model file and no evaluation output. The saved training manifest also could not support a meaningful test: its 25 malicious records are all file hashes, and its other 425 records are web and RSS text labeled unknown, which the training code counts as benign. A classifier could tell those two groups apart without learning anything about threats. So nothing on this page describes how well it classifies, and the numbers describe the design and the size of the cache.
  • The triage point values are set by hand, not learned from data.
  • The live box runs only the offline rules of the triage tool. It is not the ML pipeline, which needs its cache, models and training data, and it never calls VirusTotal, DNS or the other online checks.
  • The review queue in the saved project is empty, so it has not been exercised on stored data.
  • The optional "LLM reasoner" inside the pipeline is a placeholder: it redacts email addresses and key-like strings, then uses keyword rules. The assistant is the part that calls a real LLM.
  • The public datasets stand in for live feeds, so the cache is not real-time threat intelligence.
  • The source of the pipeline and the assistant is not published yet. The repository holds the triage tool and an architecture note with code excerpts.

Next step: train on a labeled public phishing dataset with a held-out split, report precision and recall, and compare against the hand-set score.
