CyberAI: threat triage, an ML pipeline and a cited assistant

CyberAI is a cyber-threat assistant I built for a graduate AI course. It checks links, emails and PDFs, keeps a local cache of threat indicators, scores them with machine-learning models, and answers questions from the cache before it goes online.

Relevant to: classification, logistic regression, anomaly detection (Isolation Forest), drift monitoring, human-in-the-loop review, retrieval-augmented generation, TF-IDF retrieval, sentence embeddings, API integration, SQLite, Python.

What it is

Three parts work together. A rule-based triage tool scores links, emails and PDFs from VirusTotal, DNS, WHOIS, blocklists, SPF, DMARC and DKIM checks, look-alike domains and phishing wording, and returns Clean, Suspicious or Malware with the reasons. An ML pipeline scores indicators in a local cache. A chat assistant answers questions from that cache and shows its evidence.

Live threat feeds were hard to scrape reliably, so I seeded the cache with public cybersecurity datasets from Hugging Face as stand-ins. Together with real triage results, they make up the cache.

The pipeline

  1. Ingest. Connectors write indicators (URLs, domains, text) into a local SQLite cache.
  2. Features. Numeric features from each record, plus a bag of words over its text limited to the 300 most frequent words.
  3. Score. Logistic regression returns the probability that an indicator is malicious.
  4. Outliers. An Isolation Forest (contamination 0.05, so about 5% of training points count as outliers) returns an anomaly score.
  5. Risk. An elastic-net regression predicts a 0 to 1 risk score. Its target is each record's severity field divided by 10.
  6. Drift. For each numeric feature, the monitor measures how far the new batch's mean moved from the baseline mean, in baseline standard deviations. It averages these and alerts above 0.25.
  7. Review. Any score within 0.15 of 0.5 goes to a SQLite review queue, so a person decides the cases the model is least sure about.

The assistant

The chat assistant is offline-first. If a message contains a URL, a file or an email, it runs the triage tool. Otherwise it searches the local cache with TF-IDF. Code that loads a MiniLM embedding index is in the file, but this version of the chat does not call it. It shows the answer, why it answered that way, and the evidence passages, and it appends each exchange to a chat log that the search ignores. Separately, it saves question-and-answer pairs back into the cache (the 25 pairs above: 18 triage write-ups and 7 whose saved answer is the word None), and later questions can find them. The code calls this self-training. Nothing is trained: the assistant's earlier answers become searchable evidence, so a wrong answer can come back as evidence too.

When an LLM is configured (Ollama with llama3 by default, or an OpenAI model) it writes the answer text, at temperature 0.3, from the evidence passages. These are the two prompts, as the code builds them.

You are a cybersecurity assistant. Write a clear, factual, structured answer.
Cite evidence inline with bracketed numbers [1], [2], ... referring to the sources below.
Do NOT invent facts not supported by the sources. If sources are weak or off-topic, say so briefly.
Give a thorough, multi-paragraph explanation with bullets where helpful.

Question: the question

Sources (use these for citations):
[1] path :: first 600 characters of the passage

You are a SOC analyst. Write 4-6 concise sentences summarizing this URL triage. State overall risk, why, and concrete next steps for IR.

the triage result as JSON

Both prompts give the model the facts it should use (the evidence list, the triage result) and say what shape the answer takes. The first one also tells the model what to do when the evidence is weak.

Limits

  • I have not measured accuracy. The code has a hold-out evaluation command (a random 80/20 split), but the saved project has no model file and no evaluation output. The saved training manifest also could not support a meaningful test: its 25 malicious records are all file hashes, and its other 425 records are web and RSS text labeled unknown, which the training code counts as benign. A classifier could tell those two groups apart without learning anything about threats. So nothing on this page describes how well it classifies, and the numbers describe the design and the size of the cache.
  • The triage point values are set by hand, not learned from data.
  • The review queue in the saved project is empty, so it has not been exercised on stored data.
  • The optional "LLM reasoner" inside the pipeline is a placeholder: it redacts email addresses and key-like strings, then uses keyword rules. The assistant is the part that calls a real LLM.
  • The public datasets stand in for live feeds, so the cache is not real-time threat intelligence.
  • The source of the pipeline and the assistant is not published yet. The repository holds the triage tool and an architecture note with code excerpts.

Next step: train on a labeled public phishing dataset with a held-out split, report precision and recall, and compare against the hand-set score.
